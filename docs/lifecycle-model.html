The two-gate lifecycle

Twelve stages from domain fact to published release. Two of them stop for a human — choose the path, triage a failure. The rest is a ratchet: every failure it survives becomes a mandatory checklist item, and every repo it lands in reshapes it on arrival.

Read from: pipeline.py · 11 skills · 6 state templates · CANON.md · ADR-0001/0002/0003 · scripts/*.sh · CI · ROADMAP.md · RETRO.md — then checked against a consumer repo that has run the harness ~440 times: 647 state files · 390 PR retros · 330 tracker rows · 30+ pre-push hooks · 13 CI workflows.

The loop

Stage by stage

00

Ground

Artifact KB / domain facts / CLAUDE.md canon

AI does

Drafts and patches the KB from RFPs and from the "KB Updates Needed" section of every retro.

Human does

Supplies source material; settles domain disputes.

Gate None — standing context, not a stage you pass.

At scale The harness ships nothing for this; the consumer built it anyway — docs/ai/ (9 AI-facing domain docs), llms.txt, BEST_PRACTICES_AI.md, docs/conventions/. Evidence the leg is load-bearing, not optional.

01

Plan /pipeline-strategy

Artifact docs/strategy-sessions/*.md, an ADR if directional, ROADMAP rows

AI does

The whole 8-stage strategy pipeline: survey → brainstorm → triage → cluster → present ≥2 paths → recommend.

Human does

Reads the paths and picks one.

Gate ① The real one. Stage 7 refuses to capture until a path is chosen; ADR-0003 makes this the only place /pipeline-cycle pauses by default. --auto removes it — exactly the right thing to make opt-in.

At scale Rarer than the design implies: 4 strategy sessions across ~440 runs, all at release-line boundaries (v1.0.0-readiness, v1.1-readiness). Formal planning is an event, not a cadence.

02

Select /pipeline-next

Artifact .pipeline-state/<branch>.json — the program counter

AI does

Parses ROADMAP, filters by milestone and priority, batches related tasks, instantiates the template.

Human does

Nothing.

Gate Inherited from ①.

At scale The type system got extended locally — beyond feature (172) and bugfix (168) came investigation, milestone-retro, review-existing-pr, chore, docs. Plus per-run sidecars the harness never specified: <run>-plan.md and <run>-changes.txt.

03

Build

Artifact implementation commit on a branch, CHANGELOG untouched

AI does

All of it — often several agents at once, each in its own git worktree.

Human does

Nothing.

Gate Machine only — mandatory checklist ticks plus gate_changelog_boundary. That gate exists because two implementer agents once ran concurrently on one checkout and both edited [Unreleased].

04

Verify

Artifact TESTS_PASSED / SECURITY_PASSED verdicts, self-review notes

AI does

Runs tests, the enumerated-unit inventory, and the profile's security patterns.

Human does

Nothing unless it fails.

Gate ② Verdict extraction: FAILED overrides PASSED and halts the pipeline for --resume. The only unplanned way a human gets pulled in — and it fires from Verify, Review, or a red CI alike.

At scale Self-Review is where canon accretes fastest: 9 mandatory items of 15, up from 5 in the stock template. Each addition names its incident — including a mechanical scan for private downstream-app names after one nearly shipped in a commit subject.

05

Ship

Artifact docs + CHANGELOG commit, pull request

AI does

Writes both commits and opens the PR.

Human does

Nothing. The PR is the human-legible artifact if you want one.

Gate gate_docs_only enforces the two-commit shape — code in one, docs in the other.

06

Review

Artifact PR review comment + APPROVE / REQUEST_CHANGES

AI does

A fresh subagent with no build context reads the PR cold.

Human does

Optional read.

Gate REQUEST_CHANGES loops back to Build. Context isolation is the load-bearing part — a same-session self-review would just rationalize.

07

Merge

Artifact merged PR, green CI

AI does

Squash-merges. It can't self-approve (GitHub blocks it), so it posts a review comment and merges.

Human does

Nothing.

Gate CI plus the pre-push wall — in a mature repo that's 30+ hooks (bandit, mypy, detect-secrets, cargo-audit) and a dozen workflows, not the three checks the harness repo runs on itself.

At scale Merges target the active release line, not trunk — pr_target_branch: "1.1", with a documented escape hatch to the stabilization line for P0 regressions.

08

Learn

Artifact pr/feedback/retro-N-*.md (5 sections) + a tech-debt issue per deferred finding

AI does

Writes both. Roughly 30–60 seconds per finding, and the PR still merges on schedule.

Human does

Nothing.

Gate The hard programmatic gate_retro_artifact — the pipeline cannot report done without the file on disk.

At scale 390 review artifacts on disk, and a daily CI job that scans merged PRs for a missing Stage 14 retro. The gate has an auditor.

09

Close /pipeline-retro --reconcile

Artifact RETRO.md bucket entry + Action Tracker rows

AI does

Dedupes across PR retros, files issues, updates the tracker.

Human does

Skims the tracker.

Gate Soft — verification sub-stages re-check every "Action taken:" line, so the machine audits itself. Realistically this is where a human should look and mostly doesn't.

At scale 330 tracker rows, 323 closed — and a status value the harness doesn't define, OUT-OF-REPO, on 41 rows that point at issues filed against the harness itself.

10

Release RELEASING.md · release skill

Artifact version bump, CHANGELOG cut, git tag, published package, release notes

AI does

Bumps the version, auto-increments the RC, updates the changelog, verifies, tags, publishes.

Human does

Decides when to cut — RC train vs GA, which release line, whether the soak is done.

Gate A pre-release security audit workflow, a release-workflow dependency check, and CodeQL — automated, but the cut itself is a judgment call the human makes by invoking it.

Note This stage was missing from my first draft. Merge is not shipped: real repos run RC trains (rc1→rc14 in one case), release branches, and a separate publish path. If you only model up to Merge, you model half the lifecycle.

11

Operate / Drain /pipeline-drain · /pipeline-roadmap-audit

Artifact incidents, inbound bugs, and the next drain bucket — a named batch of 5–7 issues

AI does

Batches issues into buckets, audits ROADMAP drift, diagnoses reported bugs.

Human does

Is the source of production signal. The single externally-sourced bug beat everything dogfooding found — which is what ADR-0002 was written about.

Gate terminal-state.sh — clean means stop; not clean means assemble the next bucket. Deferred issues must be closed or labelled backlog/wontfix/someday, or the loop livelocks under --auto.

At scale This is the loop, not its tail. A 4,886-line ROADMAP organised as successive drain buckets — "post-12 drain", "post-13 drain" — each shipping into the active release. Retro → issue → bucket → 5–7 PRs → retro, over and over.

The ratchet

The pipeline ships its own features through itself — every version from v0.1.0 to v0.8.0 went through these stages, and terminal-state.sh once correctly reported the milestone that built it as not-clean. That self-hosting is what makes the loop improve: a failure surfaced in one lap becomes a gate that the next lap cannot get past.

Stage 7 Self-Review shipped with 5 mandatory items. In the consumer repo it now runs 9 of 15 — and every addition names the incident that created it, down to the near-miss that put a private client's name in a commit subject. That is the ratchet, measured.

Rules climb. Where a rule lands isn't where it stays. ADR-0001 moved the quality gates from prose inside SKILL.md into scripts/pipeline-gates.sh — the same rule, one rung up, now executable by CI as well as by the agent. The ladder is a promotion path, not a filing cabinet.

The ratchet takes effect on the very next run. Templates are re-read from disk between stages, so a checklist item added after this morning's incident gates this afternoon's PR. No skill reinstall, no session restart, no waiting for the change to propagate.

It improves for everyone, not just itself. The downstream consumer files findings back at the harness under a tracker status the harness never defined — 41 of them. Fixes made there land in the templates every other repo inherits.

It reshapes to the repo

The same skill files behave differently in every repository, because four layers merge at runtime — each one able to override the last.

01

Built-in template

The stage skeleton, verdicts, and baseline mandatory items — templates/feature-state.json and friends.

02

Built-in profile

Framework-level security patterns and auto-reject triggers. Selected by detection: manage.py present → django, otherwise generic.

03

Project CLAUDE.md

Default branch, PR target, test / lint / build commands, changelog style, profile override.

04

Per-repo overrides

.pipeline-templates/ and .pipeline/profile.json — extra checklist items, patched stages, a different PR target. This is where a repo's own hard-won rules live.

/pipeline-init writes layers 3 and 4 by detection — default branch, test/lint/build commands, ROADMAP format, version scheme — and migrates a foreign-format ROADMAP into the one the parser actually reads. It was proven on a deliberately hostile repo: master instead of main, Node instead of Python, npm test, a checkbox ROADMAP. Migrated, ran end to end, PR opened against master, reviewed, squash-merged.

Same harness, two repos. Here it runs make check on a stdlib script with no test runner and targets main. There it runs 30+ pre-push hooks across Python and Rust, targets an active release branch instead of trunk, and greps every diff for private client identifiers. Nothing in skills/ differs between them — the entire difference lives in layers 3 and 4.

The skeleton survives contact. The 14-stage template is unchanged in structure — same stage names, same subagent split at Code Review / Merge / Retrospective. What grew is density: mandatory checklist items roughly doubled, and every addition cites the incident that caused it.

All four canon venues fill up, in the predicted order. CLAUDE.md carries 25 "process canonicalizations from X retro arc" sections across 1,543 lines; the pre-push wall runs 30+ hooks including repo-specific ones; CI runs 13 workflows — one of which is a daily audit for merged PRs that skipped their retro, which is precisely CANON.md's worked example, built for real.

The upstream channel is the surprise. A tracker status the harness never defined — OUT-OF-REPO — marks 41 findings blocked on the harness repo, excluded from the consumer's own open count. The consumer instrumented its feedback into the tool. That is ADR-0002's thesis running unattended.

What spans stages

Shared context

Four artifacts do the work: the state file (program counter, immune to context compression), CLAUDE.md (canon), ROADMAP.md (queue), RETRO.md + Action Tracker (memory). ADRs are the "why" layer that keeps Plan from re-litigating settled questions.

The state file is the good idea here — everything else is conventional. At scale a fifth appears that the harness doesn't specify: a one-line-per-PR ledger, with a quality score.

Guardrails

CANON.md's four-venue ladder is the most reusable thing in this repo and I'd lift it into any project: CLAUDE.md → pre-push → CI → template mandatory item, weakest guard to strongest.

The decision rule — "fires on every PR + prose discipline + not runtime-checkable → template canon" — is what stops rules from piling up in the weakest venue. Worth watching: at scale CLAUDE.md still swells to 1,500+ lines, which is the venue the ladder itself calls easiest to forget.

Tooling

pipeline.py as harness; scripts/*.sh as gates that are executables, not prose (ADR-0001); make check and make terminal-state; profiles for framework-specific security patterns; gh for issues and PRs. Concurrency comes from git worktrees — one per agent, ~20 in flight at peak.

Evals Gap

The harness ships checks (CI, gate scripts, template validator) and validation runs (foreign-repo e2e), but no eval suite. Nothing upstream measures the thing the whole design claims: does the executor still tick Stage N when context is under pressure?

Except downstream, where someone built one. A bypass-audit script plus a daily workflow scans merged PRs for missing retro markers — a real compliance measurement of the harness's central promise. It has never been promoted upstream. Adopting it, plus a fixtures directory of state files replayed to assert the executor refuses to advance past unticked mandatory items, would close this leg with work that already exists.

What should move upstream

Everything below already exists downstream and is missing from the harness. All eleven are now filed as issues #68–#78, ranked in ROADMAP.md under Future → Upstream candidates, and tracked as Action Tracker rows 12–22 (PR #79) — so the next /pipeline-strategy survey surfaces them instead of rediscovering them.

01

Retro-bypass audit

A daily scan of merged PRs for a missing Stage-14 retro marker. The highest-value item by a distance — it is the only existing measurement of the family's central promise, and CANON.md already cites exactly this as its CI-venue worked example while the harness ships no such thing.

02

Release stage

Merged ≠ shipped. RC trains, release branches, a pre-release security audit, and a publish path all run outside the model today.

03

Release-line targeting

pr_target_branch is honoured but /pipeline-init only detects the default branch, so every consumer on a release-branch model hand-edits all its templates.

04

OUT-OF-REPO status

A tracker status for findings blocked on another repo, excluded from the local open count — with a matching terminal-state.sh rule. Same livelock class as the deferred-label fix in v0.8.0.

05

PR ledger

Both repos keep a one-line-per-PR log and no skill writes it. Stage 14 should append it.

Also queued: documenting the drain-bucket cadence as the real steady state, concurrency guidance for parallel worktrees, a forbidden-identifier scan as a profile feature, the extra pipeline types invented downstream, canon-compaction guidance in CANON.md, and executor eval fixtures. Three more — the gh issue create URL-parse trap, a ROADMAP duplicate-heading guard, and a pre-commit unstaged-work-preservation reflex — are already written into the skills and waiting on a commit.

Two human gates exist in practice: choose the path and triage a failure. Everything between is machine-gated by verdicts, mandatory checklist ticks, executable gates, and CI. That's the correct allocation — humans are best at "which direction" and worst at "did stage 11 of 14 actually run," and the machine is the reverse.

What checking the model against a real consumer changed: the drain loop is the main loop. Formal planning happens about four times per release line; the other several hundred runs are retro → issue → bucket → PRs → retro. The harness under-instruments that leg, so its heaviest user hand-rolled the missing parts — bucket-structured roadmap, PR ledger, retro-bypass audit. The prototypes for the upstream fix are already written; they're just in the wrong repo.

The part worth stealing even if you never adopt the harness: a process that only gets stricter. Most conventions decay — someone documents a rule, everyone forgets it, the rule dies in a stale wiki. This one runs the other direction, because a lesson is only finished when it has been promoted to a venue that can refuse the next PR. The stage list is the visible artifact; the ratchet is the actual product.
